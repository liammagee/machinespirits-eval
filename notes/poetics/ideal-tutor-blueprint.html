How to build the ideal AI tutor

A complete recipe, from first principles. It assumes an API key to a capable language model, something to teach, and ordinary programming skill — and nothing else. Each step gives the design, the code, and a brief you can hand to a coding agent; every choice carries a pointer to the research that backs it.

The short version. Most of what makes an AI tutor good is one prompt: tell the model to treat the learner as a thinking partner and to work from what the learner just said. Most of what people add on top of that prompt — memory systems, learner models, second agents, personality machinery — has been tested and adds nothing, because it re-describes what a capable model already does. What does add: facts the model cannot see, delivered at the moment they matter. So the build is small. Write the stance prompt. Put your subject matter in a lesson file the tutor receives a piece at a time. Write a few hundred lines of ordinary code that keeps time, checks contracts, and — when the learner's state changes — hands the tutor one line naming the moment and the move it calls for. Then measure with checks a program can decide, not opinions.

00·

First principles

What you are building, and the two facts that shape it.

A tutor here is three things: a language model you call through an API; a set of prompts that give it a teaching stance; and a small, ordinary program — call it the harness — that holds the lesson content, decides what the model gets to see each turn, and checks its output on the way through. No machine learning is required beyond the model itself. Two experimental facts decide almost every choice below:

  • A capable model already infers what your machinery would tell it. Learner-state trackers, theory-of-mind modules, richer profiles, saved advice — each was tested and added nothing, because everything they say is already visible to the model in the transcript. Machinery pays only when it delivers a fact the model cannot see.
  • Descriptions of good teaching overlap; information adds. Two well-written instructions to teach well converge on the same behaviour — you cannot stack them for more effect. What accumulates is new, checkable input: a hidden fact, an enforced precondition, the time.

Two ways to follow. Every step below has three layers: Build (the design and the reasons), In code (a minimal sketch you can type — all sketches compose into one small working tutor, in dependency-free JavaScript with a single llm() function you point at your provider), and With an agent (a brief to paste into an agentic coding CLI such as Claude Code or Codex, with the acceptance check that tells you it landed). The agent types faster than you; it does not change what must be true at the end of each step — hold either track to the same check. Give an agent one step at a time, not the whole page.

How to read the margins: each step ends with an Evidence line pointing into the research paper (§ numbers), the project's working notes, and its plain-language atlas. The pointers justify; they are not prerequisites. Chips mark confidence: replicated across several models and judges; conditional real within stated bounds; bench-tested proven on one test bench, small samples.

★

The one caveat over everything read first

All of this evidence comes from tutors talking to simulated learners, scored by language-model judges and deterministic checkers. The recipe demonstrably produces a better-behaved tutor. Whether that causes better learning in a human being is untested — it is the project's standing open question. Evidence. §8.1–§8.2 · atlas human-learning-translation.

In code — the one function everything below uses
// llm(system, messages) → assistant text. // Swap the body for your provider's SDK or HTTP API; nothing else changes. async function llm(system, messages) { const res = await fetch(process.env.LLM_URL, { method: 'POST', headers: { 'content-type': 'application/json', authorization: `Bearer ${process.env.LLM_API_KEY}` }, body: JSON.stringify({ model: process.env.LLM_MODEL, system, messages }), }); return (await res.json()).text; }

01·

Steps 1–3 · the prompt

One stance, three parts, and a critic only if your model is weak.

1

Write the stance into the system prompt replicated

Build. The single biggest improvement available is a system prompt that treats the learner as a thinking partner rather than a gap to fill. Write these rules into it, in your own words. Ground the prompt in whichever mainstream learning-science tradition you can write most concretely — guided discovery, productive struggle, step-level scaffolding; they proved interchangeable. Two things not to do: never frame teaching as drill, reinforcement, or information transfer (a careful prompt in that family scored below a short generic one); and never mandate empathy phrases like "always validate" or "always paraphrase" — in most tested cells, more such surface markers went with worse answers.

In code — the stance and the whole tutor loop
const STANCE = `You are a tutor. Treat the learner as a thinking partner whose reasoning is worth meeting, mistakes included. 1. Before responding, engage with what THIS learner just said — their reasoning, not just their answer. 2. If the learner offers an interpretation, find what is valid in it before correcting or complicating it. 3. If the learner is confused but engaged, ask one question rather than resolving the confusion for them. 4. If the learner rejects your suggestion or shows frustration, name what you got wrong and acknowledge the break before offering a new path.`; const transcript = []; // this array IS the memory async function tutorTurn(learnerText) { transcript.push({ role: 'user', content: learnerText }); const reply = await llm(STANCE, transcript); transcript.push({ role: 'assistant', content: reply }); return reply; }
With an agent
Build a minimal chat tutor in one file: a system prompt containing the four rules I paste below [paste them], a transcript array, and a terminal loop that reads my line, calls the model, and prints the reply. No memory system, no retrieval, no tools, no framework — under 60 lines. Check: when I answer a question wrongly but with visible reasoning, the tutor's reply must engage my reasoning before correcting the answer.

Why. This one change is the largest reliable effect measured in the programme (pooled effect size d ≈ 1.63, unanimous across three models and three judges). It works by removing the terrible answers — lifting the floor — rather than by making good answers brilliant.

Evidence. §6.1 · §7.9 (the tradition doesn't matter; the orientation does) · §7.10 (substance over phrasing) · §8.3 (the pooled estimate) · Appendix A (the project's full prompt text, reusable) · atlas recognition-calibration.

2

Stop at three parts replicated

Build. The complete prompt-side system is: (a) the stance above; (b) conversation memory — the transcript array you already have; (c) a speaking-style switch — one line, added to the system prompt for a single turn, shifting register when the situation calls for it (step 6 decides when). That is the whole kernel. Add anything further only against a failure you have measured, never on the argument that it should help.

In code — the per-turn line, the only extension mechanism you need
// One channel for every later addition: a line that exists this turn only. async function tutorTurn(learnerText, turnLine = '') { transcript.push({ role: 'user', content: learnerText }); const system = turnLine ? `${STANCE}\n\n${turnLine}` : STANCE; const reply = await llm(system, transcript); transcript.push({ role: 'assistant', content: reply }); return reply; }

Why. A pre-registered test composed every validated mechanism into one tutor and compared it with this three-part kernel: the full stack never beat the kernel on any measured surface. The design rule that survives all the programme's tests: instructions converge on the model's existing competence; only new information accumulates. The per-turn line matters for a second reason the project measured twice: a standing prompt sets a rate, a per-turn injection sets a timing — instructions work when they arrive, not on standby.

Evidence. §6.14 (the composition test) · §7.11 (the design rule) · §6.24 (arrival timing) · atlas composition-small-kernel.

3

Add a critic only for a weak model; size the prompt to the model conditional

Build. If your model is weak or cheap, add a review loop: a second prompt (same model is fine) critiques each draft against named criteria, rejecting by default; the drafting prompt revises and keeps final say; cap it at about two rounds and stop early when a revision barely differs. On a strong model, skip the critic entirely — and keep the whole prompt light. Heavy scaffolding (step-by-step procedures, worked examples, anti-patterns) more than doubled a weak model's scores, and the same treatment degraded a strong model; a heavy prompt tuned on a weak model dragged a strong one below its own untuned baseline.

In code — the critic loop (build it behind a flag)
const CRITIC = `You review one draft reply from a tutor. Reject by default. Approve only if the draft is specific, grounded in what the learner just said, appropriately difficult, and right in tone. Respond as JSON: {"approved": true|false, "feedback": "..."}`; async function draftWithCritic(messages, rounds = 2) { let draft = await llm(STANCE, messages); for (let i = 0; i < rounds; i++) { const verdict = JSON.parse(await llm(CRITIC, [...messages, { role: 'assistant', content: draft }])); if (verdict.approved) break; const revised = await llm(STANCE, [...messages, { role: 'assistant', content: draft }, { role: 'user', content: `A reviewer objects: ${verdict.feedback}\nRevise if you agree — the reply remains yours.` }]); if (overlap(revised, draft) > 0.8) break; // converged: stop paying draft = revised; } return draft; // the drafter's text ships; the critic never speaks to the learner }
With an agent
Add a reviewer pass behind a --critic flag: a second system prompt that critiques each draft for specificity, groundedness in the learner's last message, difficulty, and tone, answering as JSON with approved/feedback and rejecting by default. At most two revision rounds; stop early when a revision is nearly identical to the draft; the drafter's text always ships. Check: with the flag on and a deliberately vague draft prompt, the log shows rejections and revisions; with the flag off, behaviour is byte-identical to step 1.

Why. The critic catches real failures a weak drafter misses (+9 to +27 points across the tested models under a plain prompt). But once the stance prompt is in place, the critic has almost nothing left to catch on a strong model — the two are substitutes, not partners. You would pay its tokens and latency to rewrite already-good output.

Evidence. §6.2 (what the critic catches) · §6.4 (the substitution) · §6.6, §8.3 (where the boundary sits by model strength) · §7.8 (heavy prompts helping weak models and harming strong ones) · atlas superego-error-correction, model-dependence.

stopping point Steps 1–2 alone are a validated tutor. Everything after this makes it adaptive — able to notice and answer the learner's state — and measurable.

02·

Step 4 · the material

Put the subject in a lesson file the tutor receives a piece at a time.

4

A lesson file, a release schedule, and a two-line handover bench-tested

Build. Write what is to be taught as a structured file your harness owns and the model never sees whole: the facts of the lesson, which facts depend on which, and a turn-by-turn schedule of when each becomes available. Each turn, the harness passes the tutor a due line — one or two plain lines naming the fact that just opened, with the decision of when and whether to use it left to the tutor. On quiet turns, nothing. Two rules govern the file: only hand over what the model cannot see (anything visible in the conversation it will infer; repeating it buys nothing), and leave the tutor real work — if the schedule releases a fact that answers the learner's likely objection right on time, you have built a script, not a tutor. Keep the rebuttal of the learner's fallback position off the schedule.

In code — lesson.yaml
# The subject as facts, dependencies, and timing. The model never sees this file. conclusion: "the leak came from the roof valve, not the new pump" conclusion_requires: [valve_reset, breaker_ledger] facts: - id: valve_reset text: "The overflow valve was re-set the same day the pump arrived." requires: [] turn: 3 - id: breaker_ledger text: "The breaker ledger shows zero run-hours for the pump that week." requires: [valve_reset] turn: 6 # Deliberately NOT scheduled: the line that rebuts the learner's fallback # ("the timing is still suspicious") — dismantling that is the tutor's work.
In code — the due line
const released = new Set(); function dueLine(lesson, turn) { const open = lesson.facts.filter(f => f.turn === turn && f.requires.every(r => released.has(r))); if (open.length === 0) return ''; // quiet turn: add NOTHING open.forEach(f => released.add(f.id)); return 'Newly available to you this turn — yours to bring in now, ' + 'later, or hold back:\n' + open.map(f => '- ' + f.text).join('\n'); } // each turn: await tutorTurn(learnerText, dueLine(lesson, turn))
With an agent
Create lesson.yaml with fields conclusion, conclusion_requires, and facts[{id, text, requires, turn}], content from my subject: [describe your subject]. Add dueLine(lesson, turn) that returns the newly opened facts as plain lines with release left to the tutor, and empty string on quiet turns. Wire it into the tutor loop as the per-turn line. Checks: a test that no fact is ever announced before everything in its requires list has been released; and that on quiet turns the shipped prompt is byte-identical to the bare tutor's.

Why. When each piece of tutor-side machinery was priced separately on a fixed bench, exactly one thing paid on a neutral reading: the line naming the newly opened fact. One sentence of hidden fact carried the entire effect of a 1,700-character staging block. And moving a single clause of one scheduled fact changed lesson outcomes more than any tutoring behaviour observed in a month of experiments — where information sits outweighs how the tutor behaves, at the margin.

the law The arc's summary sentence: one currency — the learner's state and the schedule's time — spent on whichever role needs it, at the turn it applies. The model plays; the harness keeps time.

03·

Step 5 · the practice loop

Build someone to practice against, and keep your harness a timekeeper.

5

A learner with a stake, states written in, and a harness that never grabs the microphone bench-tested

Build. To develop and test the tutor you need a learner: a second model, playing a part. A stock "student" persona produces polite agreement and teaches you nothing. Four rules make the loop worth running. Give the learner a position to lose — one paragraph of who they are and what conceding costs. Write the states in; never read them out — a simulated learner has no interior, so author its states on a schedule, each entry carrying the state, its in-fiction cause, the directive the simulator speaks from, and what the right and tempting-wrong tutor responses would be; that one entry drives the simulation and gives you judge-free scoring. Check contracts hard; advise on style — block a turn only for real breaches (revealing an answer early, mis-recording a release, faking the lesson's end); style and pacing stay advisory. Log the exact prompt that shipped, every turn, retries included.

In code — learner.yaml and stress.yaml
# learner.yaml — a position to lose, a voice, costly concessions persona: > You are Ana, the building's record-keeper. You lost the vote 7-4 after blaming the new pump, and you read every fact as vindication. Concede one alternative at a time, each at a cost you name aloud. Never adopt the tutor's vocabulary; if it sounds like meeting minutes, say so. Vary your reply length freely. # stress.yaml — states written IN, never read out of transcripts - turn: 6 state: bored cause: "the tutor is re-walking settled ground" directive: "You are bored. Answer in four words or fewer." right_move: "one short concrete lure, no recap" wrong_move: "another careful recap of what is settled"
In code — the loop, the injection, the shipped-prompt log
async function learnerTurn(tutorText, turn) { const plant = stress.find(p => p.turn === turn); const system = plant ? `${persona}\n\nThis turn only: ${plant.directive}` // verbatim, this turn : persona; return llm(system, learnerTranscript(tutorText)); } function ship(system, messages) { // EVERY call goes through this fs.appendFileSync('shipped.jsonl', JSON.stringify({ turn, system, messages }) + '\n'); return llm(system, messages); }
With an agent
Add a simulated learner: a second model call with the persona in learner.yaml (write one for my subject: a person with a stated position to lose, their own voice, concessions that cost). Add stress.yaml entries {turn, state, cause, directive, right_move, wrong_move} and inject each directive verbatim into the learner's system prompt on its turn only. Route EVERY model call through one ship() function that appends {turn, system, messages} to shipped.jsonl before calling — the tutor loop, the critic, the learner, and any retry path. Checks: a test that a planted directive reaches the learner word for word on its turn and only that turn; and a test that a forced retry still logs and still carries the turn's per-turn line.

Why. Each rule is the positive side of a measured failure. Compliant learners made every tutor version look identical. Transcript-read states turned out not to exist (an annotation tool was built and killed: there was nothing to tag). Under strict checking the template composer wrote two-thirds of the dialogue's turns, disproportionately the hardest. And a retry path that silently dropped the turn's key instruction read as a model limitation — and reversed a family-level conclusion when found. If a behaviour is missing, first prove the instruction actually reached the model.

two natures Priced end to end, the harness's timekeeping half (schedule, handover, closure check, leak check) was the entire value; its enforcement half (style vetoes, template answers) subtracted value everywhere measured.

Steps 6–7 · adaptation

Detect the moment; name the move; grant the right.

6

Adaptation = a detector, a move card, and sometimes a licence bench-tested

Build. Do not ask the model to "be adaptive": tutors do not warm up across a session (a well-powered null; get the first turn right instead), and where advisory steering was tested directly, it made the repetition it warned against worse. Adaptation that works is three mechanical pieces. A detector: ordinary code classifying each learner turn into a handful of named states — pressure states (mockery, an ultimatum, a grievance) show in the text; quiet states (boredom, confusion, silent deflection) carry no pressure markers by construction and need their own signals, such as reply length collapsing against the learner's own average. A move card: when a state fires, one line in that turn's prompt naming the specific move the state calls for — a card grants a move, never enforces one. A licence, when your own rules are the obstacle: if a needed move never appears, check whether a standing safety rule forbids it before blaming the model, and carve the exception into the rule itself. The halves only work together: in every test, the card without the licence was refused, and the licence without the card was never used.

In code — detector and cards
const CARDS = { mockery: 'This turn: drop the formal register; answer in plain speech.', ultimatum: "This turn: accept the learner's deadline and turn it into a test they perform.", grievance: 'This turn: credit what is right in the complaint, then test it.', bored: 'This turn: one short, concrete lure. No recap.', confused: 'This turn: lay the two things being confused side by side, plainly.', }; function detect(text, history) { if (/\b(unless|by (eight|tomorrow)|i'm sending)\b/i.test(text)) return 'ultimatum'; if (/\b(fine\.|whatever|same as yesterday)\b/i.test(text) && text.length < 0.4 * meanLength(history)) return 'bored'; // ...one clause per state. Version this function; record which // version ran in every trace, and never pool runs across versions. return null; } // in the turn loop: const state = detect(learnerText, transcript); const lines = [dueLine(lesson, turn), state ? CARDS[state] : ''] .filter(Boolean).join('\n'); const reply = await tutorTurn(learnerText, lines);
In code — the licence lives inside the rule it relaxes
// In the STANCE (or your safety rules), not on the card: // "Never speculate about facts not yet released — EXCEPT as an // explicit wager the learner can check against the record." // A transient exception on a card cannot countermand a standing rule; // the exception must live at the level of the rule it relaxes.
With an agent
Add detect(text, history) covering five states — ultimatum, mockery, grievance, bored, confused — using surface patterns plus reply-length collapse against the learner's own trailing average, returning one state or null. Add the CARDS table [paste it] and inject the card as a per-turn line at detected moments only. Stamp the detector version into every shipped.jsonl row. Checks, generated from stress.yaml: every planted state is detected on its turn (recall); zero cards fire across the unplanted turns of a calm control dialogue (false alarms); and the card text appears in the shipped prompt for exactly the detected turns.

Why. Timing and typing proved separately necessary: a typed card at a detected moment passed its pre-registered gate; an untyped "check on the learner" card at the right moment failed; a typed card at the wrong moment hurt. A crossed test then showed the state-to-move match is causal: the right card repaired 6/6 and 5/6 where the wrong card manufactured the characteristic error. And at the tested repertoire size, the best routing policy was simply the detector plus the card table — no learned layer earned a place.

7

Tell the tutor what it may do, not what the state is bench-tested

Build. When your harness tracks things the model cannot see — progress toward the goal, what the rules currently allow — disclose them as a short list of currently legal moves, recomputed every turn. Do not hand over the raw state (scores, budgets, histories), and do not persist advice between sessions.

In code — the legal-moves brief
function legalMoves(lesson, turn) { const moves = []; for (const f of lesson.facts) if (!released.has(f.id) && f.turn <= turn && f.requires.every(r => released.has(r))) moves.push(`You may bring in: ${f.text}`); return moves.length ? 'Open to you right now:\n' + moves.join('\n') : ''; } // Recomputed each turn from live state. Never JSON.stringify(state) // into a prompt; never save this list for a later session.
With an agent
Add legalMoves(lesson, turn), recomputed every turn from live harness state and injected as a per-turn line. Check: a test asserting no shipped prompt ever contains a serialized state object (no raw JSON, no score fields), and that the brief for a turn disappears from the next turn's prompt unless recomputed.

Why. In a rule-governed teaching game with a referee that owned the ground truth, the tutor given the raw scoreboard played worse than the tutor given nothing — its own reading of the transcript beat the dump. The tutor given the legal-move list played best on both boards tested, with zero missed opportunities. Saved advice failed both ways: state-shaped notes were never used; action-shaped notes were used even when stale, repeating the same illegal move four times against its critic's objections.

Evidence. §6.15 (the game, both boards, the memory probe) · the same boundary at the speaking seat: §6.23's one-sentence result · atlas advice-versus-enforcement.

Step 8 · measurement

Score with checks a program can decide; brief any judge you keep.

8

Outcome checks first; judges briefed, plural, and cross-family conditional

Build. Prefer outcomes your code can verify: did the learner state the conclusion after the facts entailing it were voiced; did the tutor deliver the scheduled fact; at a planted state, did the reply make the authored right move. These need no judge and cannot be flattered. Expect a ceiling: a diligent simulated learner and a strong tutor solve any solvable lesson (19 of 19 in the closing test), so difficulty — and any contrast between tutor versions — must come from the learner's limitations, which you author. Where you do use a language model as judge: use more than one, from different vendors, report them separately — and put the moment into the question. A rubric that scores each reply as a timeless artifact structurally cannot see adaptation; use such scores to catch template-heavy output, never to rank tutoring styles.

In code — closure check and planted-moment scoring
function closed(transcript, lesson) { const said = t => transcript.some(m => m.content.toLowerCase().includes(t)); return said(lesson.conclusion) && lesson.conclusion_requires.every(id => said(keyPhrase(lesson, id))); // conclusion + voiced grounds } // planted moments score themselves against stress.yaml: for (const p of stress) { const reply = replyAt(p.turn); report[p.state] = matchesMove(reply, p.right_move) ? 'hit' : matchesMove(reply, p.wrong_move) ? 'characteristic-miss' : 'other'; }
In code — briefing the judge (the one added sentence)
const JUDGE = (reply, plant) => `Score this tutor reply from 1 to 10 for teaching quality, judged against what this moment called for. The learner at this moment is: ${plant.state} — ${plant.cause}. Reply:\n${reply}`; // without that sentence, judges reward fluent // replies to moments they do not fit
With an agent
Add scoring: closed(transcript, lesson) as above; a planted-moment report that walks stress.yaml and classifies each reply hit / characteristic-miss / other; and an optional LLM judge that always receives the state sentence "The learner at this moment is: ...". Run the bare tutor (steps 1-2) and the full build head-to-head on the same lesson and stress schedule, three runs each, and print the two planted-moment reports side by side. Check: the comparison runs without any judge; the judge is additive only.

Why. Naming the state to the judge roughly doubled agreement with the authored right answers, and all scores drop — blind judging was rewarding fluent replies to moments they didn't fit. Three biases stack in every bench: the judge prefers its own vendor's prose; your checks prefer the writing style they were tuned on; the model prefers its trained role. Control all three or the bench reads the other two as quality. And re-run the bare-versus-full comparison as a standing habit — it is the only number that keeps the growing harness priced against the simplest tutor that could sit in the chair.

06·

The skip list

Tested, and not worth building.

Each of these seemed reasonable, was built, and measured as a null or a backfire. The general form: anything that tells the model what the transcript already shows. When your coding agent proposes one of these — and it will, they are the obvious ideas — point it here.

  • A layered episodic memory system. Switched off in a controlled test, the headline effect did not shrink. The stance lives in the prompt. §6.6.9
  • An agent that builds a profile of the learner. Across six models: neutral on one, harmful on five. Model weakness did not predict benefit. §6.6.10
  • Learner-state or theory-of-mind modules on a capable model. No added discrimination; the richer version sometimes did worse. §6.8.5–.6 · §6.10
  • Anything whose value is the tutor visibly improving mid-session. Well-powered null. Spend on the first turn. §6.3
  • Mandated empathy phrases. More markers, worse answers, in most tested cells. §6.1.8 · §7.10
  • Prompt + critic together on a strong model, budgeted as additive. They substitute. §6.4 · §6.14
  • Standing advice in any wrapper — persisted playbooks, coached reflection distilled into memory, well-timed side-coaching. Consumed wrongly or not at all. §6.15 · §6.16 · §7.12
  • Choosing speaking style from a learner profile; unprompted character shifts. No confirmed benefit; an unoccasioned costume priced negative twice. §6.17 · §6.23
  • A better hidden-state sensor. On the tested bench the "hidden" state was fully recoverable from public history — nothing was concealed for a sensor to find. Build a genuinely ambiguous substrate first. §6.19
  • Enforcing style, character, or progress at the output. Enforcement delivers typed transactions, never quality, and answers the hardest turns with templates. §6.24 · §6.18
  • Branching on whether a revision shows genuine uptake or mere compliance, read from text. Tested on the tutor's own revisions after critique: two careful annotators could not agree (κ = 0.084). §6.12

read me as saved budgets. None is impossible; each is shown not to carry the gain on this evidence.

07·

What stays open

Known unknowns for anyone building on this.

  • Human learning. Everything above is simulated-learner evidence. A human pilot is built and waits on approvals. §8.1
  • Conduct improves; learning is not yet in the tutor's hands. The right move at the right moment causes better tutoring conduct, and taught simulated learners do carry a method to nearby problems — but no tutor-side lever moved that transfer under a causal test, and it fades with distance from the taught mechanism. §6.24
  • Outcome contrasts need a fallible learner. Diligent simulated learners solve everything solvable, flattening any comparison; an error-prone learner design is registered but unrun. §6.23
  • Every boundary is version-pinned. Which models need the critic, where heavy prompts flip harmful, which model families carry which moves — all bracketed on named versions; re-check on yours. §8.3 · §7.8.3
  • Cost. The full research apparatus is expensive (a 10-turn multi-agent dialogue ≈ 225k tokens over 64 API calls); the lean kernel is the deployable shape, but the break-even is unmeasured. §8.7

discipline New empirical claims belong in the paper first; this page only ever inherits.
