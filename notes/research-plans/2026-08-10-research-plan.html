P1 · Does the Writing Pad accumulate like an immune memory, or overwrite? — "AgentAntibody: An Adaptive Immune System for Defending LLM Agents against Prompt Injection" (2608.04053)

Why: AgentAntibody's core move is a persistent, cross-turn library that adds a new record on a novel case and reuses a matching one otherwise, instead of starting cold each turn. Cell 21 (cell_21_recog_multi_unified_rewrite in config/tutor-agents.yaml) runs on exactly this kind of persistent artifact — the Writing Pad (services/memory/tutorWritingPad.js, services/memory/learnerWritingPad.js) — but nothing in the project currently checks whether it behaves like AgentAntibody's library (grows, keeps distinct records, compacts) or like a single overwritten snapshot.
Do: read-only check, no new runs. Read updateTutorWritingPad / updateConsciousState and updateConsciousLayer / recordBreakthrough / recordTrauma / recordLesson in services/learnerTutorInteractionEngine.js against the writingPadSnapshots.before / .after pairs already captured in existing cell 21 interaction traces. Track snapshot size and distinct-record count turn over turn across an existing multi-turn cell 21 run: does the pad grow and keep prior records legible (antibody-library behaviour) or does each turn's write replace the last one's content (stateless overwrite)?
Evaluate: existing dialogue logs / interaction traces for any already-run cell 21 session — a small script or manual read over the recorded writingPadSnapshots sequence. No new generation, no model calls. existing data
Note: the roundup also flags cells 110-125 (trap-scenario suite) as lacking any persistent memory of which traps a given learner has already tried across turns — a real gap, but adding that memory is new code plus a new eval, not a read-only check. Leave it as a named backlog candidate rather than folding it into P1.

P2 · Is "human takes one role, AI plays the rest" generic, or hardwired to tutor/learner? — "AgentForge: An Immersive Role-Playing Platform for Learning Agentic Software Engineering" (2608.04148)

Why: AgentForge lets a novice pick any one of four roles in a multi-agent workflow while AI plays the other three. This project already has the same shape for one fixed pair — a human plays the learner while the tutor is AI-played, via /ms-play-tutor and /ms-tutor-remote, and the pilot infrastructure (services/pilotStore.js, public/pilot/index.html). AgentForge's four-role rotation asks whether that swap is generic — could a human instead take the superego's seat, or a cast member's role in an id-director drama — or whether it only works because tutor/learner is the one pairing that got built.
Do: design audit, no new code. Read the /ms-play-tutor and /ms-tutor-remote skill implementations plus services/idDirectorEngine.js's cast construction to find out which role a human can stand in for today, and where the coupling to "human = learner" is a config value versus baked into the control flow. Produce a short list: which roles are swappable now (config change), which would need new plumbing (structural change).
Evaluate: no eval run — this is a design-fit report, not a scored comparison. If the audit finds a role is already swappable, a follow-up item could try it on an existing drama transcript; that is a separate, later decision. existing code / design audit
