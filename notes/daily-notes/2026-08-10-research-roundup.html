Prompt Engineering

AgentAntibody: An Adaptive Immune System for Defending LLM Agents against Prompt Injection UNBLOCK

Shihao Weng, Yang Feng, Xiaofei Xie, Jiongchi Yu · arXiv 2608.04053 · August 4, 2026 · https://arxiv.org/abs/2608.04053

Notes that most prompt-injection defenses treat each task as a self-contained problem and forget what they learned once it's done, even though user requests are often underspecified — the agent doesn't fully know what behavior the user would reject until it happens once. AgentAntibody keeps a persistent library of "antibodies," each one an evolving record of the user's security boundary built from past encounters, and checks new requests against that library at runtime rather than starting cold every time.

Project relevance: A close structural cousin of cell 21's dynamic prompt rewriting with the Writing Pad — both keep a persistent, cross-turn text artifact that accumulates what the agent has learned rather than treating each turn as stateless. AgentAntibody's update rule (add a new antibody on each novel threat, reuse a matching one otherwise) is a concrete design to check the Writing Pad against: does it accumulate and compact the way an immune memory does, or does it overwrite? The same online, per-encounter learning pattern is also a candidate lens for the trap-scenario suite (cells 110-125), where the adaptive tutor currently has no persistent memory of which traps a given learner has already tried across turns.

Agent Architecture

Architectural Implications of Agentic AI Workflows WATCH

Jirong Yang, Peizhe Liu, Chaojie Zhang, Jovan Stojkovic · arXiv 2608.04458 · August 5, 2026 · https://arxiv.org/abs/2608.04458

The first architectural characterization of agentic AI workloads, combining a production study at Microsoft Azure with a controlled study of open-source frameworks. Finds that a single agent request fragments into a workflow of LLM calls, tool invocations, and orchestration decisions that keep crossing the CPU-GPU boundary, so the CPU — running orchestration and tools, not the model — sits on the critical path, and demand stays low with sudden spikes rather than steady load. They prototype a server, Agora, that harvests idle CPU cores for other work while protecting agent tail latency against those spikes.

Project relevance: Datacenter-level, not pedagogy-level, so background rather than actionable. Still a useful frame for the eval harness's own runtime cost: each ego-superego turn in `evaluationRunner.js` is exactly the fragmented LLM-call-plus-orchestration pattern the paper characterizes, and its finding that orchestration (not model inference) is the bottleneck matches informal experience running large parallel batches through `eval-cli.js run --parallelism N` — worth a look next time cost or latency tuning for a big multi-cell run comes up (`scripts/test-latency.js`, `services/adaptiveTutor/budgetTracker.js`).

Agent Against Agent: An Agentic System for Automatic Prompt Injection Red Teaming WATCH

Yanting Wang, Chenlong Yin, Runpeng Geng, Jinyuan Jia · arXiv 2608.05108 · August 5, 2026 · https://arxiv.org/abs/2608.05108

PIMiner is an attacker agent that trains on a sequence of (dataset, target-model) pairs and builds a strategy library from scratch, rather than a single reinforcement-learned attacker that generalizes poorly to unseen targets. At test time the learned library transfers directly to a new target LLM with no retraining, needing only about ten queries per test sample.

Project relevance: Background only — this is adversarial security tooling, not pedagogy. But the shape (one agent repeatedly probing another and distilling a transferable strategy library from the exchanges) is structurally close to the divergent-superego cells (22-33), where a `dialectical_suspicious` superego repeatedly probes the ego's response. Worth a skim if `services/dialogueTraceAnalyzer.js` ever needs a model for turning per-run superego critiques into a reusable, cross-run strategy set rather than scoring each run's deliberation independently.

Dramaturgy / Role-Play

AgentForge: An Immersive Role-Playing Platform for Learning Agentic Software Engineering UNBLOCK

Zihan Fang, Yueke Zhang, Yu Huang · arXiv 2608.04148 · August 4, 2026 · https://arxiv.org/abs/2608.04148

Points out that agentic AI now coordinates planning, implementation, review, and testing in software work but gives novices little visibility into how it decides, making it hard to learn both how the agent works and how to judge its output. AgentForge answers this by having a novice pick one of four roles in a multi-agent code-repair workflow — Task Planner, Patch Author, Code Reviewer, Test Runner — while AI agents play the other three, so the human sits inside the workflow rather than watching it from outside.

Project relevance: A close match to a standing design choice here: the learner is a full LLM agent with its own deliberation, not a scripted role (`services/learnerTutorInteractionEngine.js`), and the human-learner pilot (`services/pilotStore.js`, `public/pilot/index.html`) and the `/ms-play-tutor` / `/ms-tutor-remote` skills already let a human step into one role of a dialogue while the rest of the cast is AI-played. AgentForge's four-role rotation is a concrete template for extending that beyond the tutor/learner dyad — a human could take any one of several roles in a drama's cast while the others run as usual, which is a different axis of variation than the current single-swap pilot mode.
